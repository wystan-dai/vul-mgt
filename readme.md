## 1. 项目背景与目标

### 1.1 建设背景

随着国家关键信息基础设施安全防护要求不断提高,需要建设统一的漏洞情报汇聚、资产风险管理、通报预警与整改闭环平台,实现对国家/行业范围内网络资产漏洞的**发现—评估—通报—整改—复核—统计**全生命周期管理。

### 1.2 建设目标

- 建立统一的漏洞知识库,汇聚 CVE、CNVD、CNNVD、厂商公告等多源漏洞情报
- 实现跨部门、跨行业、跨地域的资产漏洞统一管理与风险量化评估
- 建立标准化的漏洞通报、整改、复核工作流,缩短平均修复时间(MTTR)
- 满足等级保护、密码合规、数据分级分类等国家安全合规要求
- 支撑多角色(国家级监管、行业监管、属地监管、企业用户、公众)差异化访问需求

### 1.3 核心设计原则

| 原则 | 说明 |
|---|---|
| 安全优先 | 全链路国密改造、分级授权、审计留痕,安全设计先于功能设计 |
| 数据主权 | 核心数据、算力、存储均需支持信创环境私有化部署 |
| 松耦合微服务 | 各功能模块独立部署、独立扩缩容,通过消息总线解耦 |
| 标准化对接 | 预留标准接口(参考 STIX/TAXII),便于下级系统/兄弟单位接入 |
| 可审计可追溯 | 关键操作(查看、导出、通报、整改确认)全程留痕且防篡改 |

## 2. 总体架构设计

### 2.1 架构分层

```
┌─────────────────────────────────────────────────────────┐
│  用户层:国家级监管 / 行业监管 / 属地监管 / 企业用户 / 公众    │
└───────────────────────┬─────────────────────────────────┘
                         │
┌───────────────────────▼─────────────────────────────────┐
│  接入层:CDN、WAF、抗DDoS、国密SSL终止                        │
└───────────────────────┬─────────────────────────────────┘
                         │
┌───────────────────────▼─────────────────────────────────┐
│  网关层:API网关、统一身份认证(SSO)、限流熔断、灰度路由        │
└───────────────────────┬─────────────────────────────────┘
                         │
┌───────────────────────▼─────────────────────────────────┐
│  应用服务层(微服务集群,经内部消息总线解耦通信):               │
│  情报采集 | 漏洞知识库 | 资产测绘 | 扫描编排 | 风险评分       │
│  工单闭环 | 通报预警 | 权限中心 | 审计中心 | 报表大屏         │
└───────────────────────┬─────────────────────────────────┘
                         │
┌───────────────────────▼─────────────────────────────────┐
│  数据与消息层:Kafka、PostgreSQL、Elasticsearch、Redis、      │
│  MinIO(对象存储)、Neo4j(可选,攻击面关联)                   │
└───────────────────────┬─────────────────────────────────┘
                         │
┌───────────────────────▼─────────────────────────────────┐
│  基础设施层:Kubernetes(信创发行版)、多地容灾、CI/CD          │
└─────────────────────────────────────────────────────────┘

  贯穿全链路:审计日志 | 密评合规 | 等保三级/四级 | 数据分级分类
```

### 2.2 架构设计要点

- **接入层与网关层物理隔离**:接入层部署在 DMZ 区,网关层及以下部署在内网可信区,中间通过单向/双向网闸或严格的安全域策略隔离
- **应用服务层按业务域拆分微服务**,每个服务独立数据库 schema(避免跨服务直接读写对方数据库),服务间通过 API/消息队列通信
- **消息总线(Kafka)是核心解耦机制**:情报采集→清洗→入库→评分→通报的链路以事件驱动方式串联,任一环节故障不影响上游数据持续接收
- **多租户隔离设计**:不同部委/省份/行业的数据在逻辑层(schema/租户ID)隔离,必要时可物理隔离部署独立集群,同时提供国家层面的跨租户汇总统计能力(需专门的汇总服务+脱敏机制)

## 3. 功能模块详细需求

以下每个模块均按【功能描述】【详细需求点】【输入/输出】【关键非功能要求】四部分展开,供研发直接拆解为任务。

### 3.1 漏洞情报采集模块(Intelligence Collector）

**功能描述**:多源采集国内外权威漏洞情报源数据,统一清洗、去重、标准化后写入知识库。

**详细需求点**:
- 支持对接的情报源类型:
  - 国际:NVD/CVE、GitHub Security Advisories、厂商安全公告(Microsoft MSRC、Oracle CPU、Adobe、Cisco PSIRT 等)
  - 国内:CNVD、CNNVD、国家信息安全漏洞库、各安全厂商情报订阅(奇安信、绿盟、启明星辰等,如有商业授权)
  - 补充源:GitHub PoC 仓库监控、Exploit-DB、暗网监控情报(如有合规渠道)
- 采集方式需同时支持:定时拉取(API/RSS)、推送接收(Webhook)、文件导入(离线场景)
- 原始数据先落"原始数据湖"(不做任何清洗,保留原文,用于溯源和合规审计),再经清洗管道处理
- 清洗管道能力:字段标准化映射(不同源字段名不同需统一 schema)、去重(同一 CVE 多源合并)、语言归一化(英文摘要机器翻译+人工复核标记)、附件下载与病毒扫描(PoC/EXP 文件)
- 采集任务需可视化配置与监控(采集频率、成功率、最近失败原因)
- 需支持人工补录接口(供分析师手工录入未公开或内部发现的漏洞)

**输入**:各情报源 API/RSS/Webhook 数据、人工补录表单
**输出**:标准化漏洞情报事件(写入 Kafka topic `raw.vuln.intel`),供下游知识库服务消费

**关键非功能要求**:
- 采集延迟:公开高危漏洞发布后 30 分钟内完成采集入库
- 采集任务失败需自动重试(指数退避)并告警
- 单日采集量预留至少 10 万条事件的吞吐能力

---

### 3.2 漏洞知识库模块(Vulnerability Knowledge Base）

**功能描述**:漏洞主数据管理中心,是全平台的数据核心。

**详细需求点**:
- 漏洞主数据模型字段(最小集合,可扩展):
  - 基础信息:漏洞编号(CVE/CNVD/CNNVD/内部编号)、名称、描述(中英文)、发现时间、公开时间
  - 技术信息:漏洞类型(CWE分类)、受影响厂商/产品/版本范围、攻击向量、攻击复杂度
  - 评分信息:CVSS v3.1 基础分/时间分/环境分、EPSS 分数、厂商自评级别
  - 利用信息:是否有公开 PoC/EXP、是否已发现在野利用、利用难度
  - 修复信息:补丁链接、临时缓解措施、官方公告链接
  - 分级信息:数据敏感级别(公开/内部/涉密)、审批状态
- 支持漏洞版本变更历史追溯(比如 CVSS 分数被厂商后续调整,需保留变更记录)
- 支持漏洞与漏洞之间的关联关系(如同一供应链组件引发的多个 CVE、漏洞链利用关系)
- 全文检索能力:按厂商、产品、版本、CWE类型、时间范围、评分区间等多维组合查询
- 支持漏洞信息分级发布机制:内部可见 → 脱敏公开 → 完全公开,三阶段需有时间窗口配置和审批流

**输入**:情报采集模块清洗后的标准化事件、人工审核/补充
**输出**:对外查询 API、对内供风险评分/资产关联使用的数据服务

**关键非功能要求**:
- 检索响应时间:P95 < 500ms(基于 Elasticsearch)
- 知识库数据量预留:500 万条漏洞记录、年增长 50 万条的容量规划

### 3.3 资产管理与测绘模块(Asset Management & Discovery）

**功能描述**:维护全域资产台账,并通过主动/被动方式持续发现资产及其暴露面。

**详细需求点**:
- 资产录入三种方式:
  1. 企业/单位自主填报(Web表单/批量导入模板)
  2. 主动测绘(基于 IP 段/域名的端口扫描、指纹识别、组件识别)
  3. 被动流量识别(镜像流量分析、DNS 日志分析识别影子资产)
- 资产台账字段:资产标识(IP/域名/主机名)、责任单位、责任人、资产类型(服务器/网络设备/IoT/云资产)、重要性等级、所属业务系统、部署环境(生产/测试)
- 资产指纹识别需支持常见组件(操作系统、Web中间件、数据库、开源组件版本)识别,作为漏洞匹配的基础
- 资产变更需有版本历史(新增/下线/变更责任人)
- 资产与漏洞自动关联:基于指纹信息,新漏洞入库后自动匹配存量资产,生成风险事件
- 资产重要性分级需支持自定义评估模型(业务影响面、数据敏感度、是否互联网可达)

**输入**:企业填报数据、扫描引擎回传数据、流量分析结果
**输出**:资产台账数据(供风险评分、通报模块使用)、资产-漏洞关联事件

**关键非功能要求**:
- 支撑资产规模:单租户不低于 100 万资产节点
- 主动测绘任务需有严格的**授权范围控制**,超出授权 IP 段的探测请求必须被拒绝并告警(法律合规红线)

### 3.4 扫描编排模块(Scan Orchestration）

**功能描述**:统一调度多种扫描引擎,对已授权资产执行漏洞扫描任务。

**详细需求点**:
- 插件化对接多种扫描引擎:开源(OpenVAS、Nuclei)、商业(Nessus等,如有授权)、自研 POC 引擎
- 通过统一 Agent/API 抽象层屏蔽底层扫描器差异,上层业务无需感知具体用的哪个引擎
- 扫描任务管理:任务创建(选择资产范围+扫描策略+扫描窗口)、任务队列削峰(避免并发扫描过载目标网络或扫描器自身)、任务进度追踪、扫描报告归档
- 扫描策略模板化:全端口扫描、Web应用扫描、特定CVE专项扫描(比如某高危漏洞爆发后的全网专项排查)
- 扫描结果自动回填资产台账指纹信息,自动生成漏洞事件进入工单流程
- 需支持"仅探测不攻击"的安全模式(避免扫描本身对生产系统造成影响),POC验证类扫描需二次授权确认

**输入**:扫描任务配置、资产台账、漏洞知识库(POC匹配规则)
**输出**:扫描结果报告、漏洞事件(推送至工单闭环模块)

**关键非功能要求**:
- 扫描任务并发控制:同一网段并发扫描连接数可配置上限,防止误伤业务系统
- 扫描全程操作留痕,任务发起人、授权范围、执行时间窗口均需审计记录

### 3.5 风险评分与优先级模块(Risk Scoring Engine）

**功能描述**:综合多维因素对漏洞-资产组合进行风险量化,输出处置优先级。

**详细需求点**:
- 评分模型 = CVSS基础分 + EPSS利用概率 + 资产重要性权重 + 网络暴露面系数 + 在野利用情报加权
- 评分规则需可配置(规则引擎实现,而非硬编码),便于策略随国家/行业通报要求调整
- 支持自定义评分模板:不同行业(金融/能源/政务)可使用不同权重配置
- 输出风险等级:极高危 / 高危 / 中危 / 低危,并给出处置时限建议(SLA基准,如极高危24小时内响应)
- 需支持批量重新评分(比如某漏洞被曝出在野利用后,存量所有关联资产风险等级批量上调并触发通报)

**输入**:漏洞知识库数据、资产台账数据、外部利用情报
**输出**:风险评分事件(推送至工单闭环、通报预警模块)

**关键非功能要求**:
- 批量重新评分:10万级资产-漏洞组合重新评分需在30分钟内完成

---

### 3.6 工单闭环模块(Workflow & Remediation）

**功能描述**:管理漏洞从发现到修复确认的完整工作流。

**详细需求点**:
- 标准工作流节点:漏洞发现 → 自动/人工派单 → 责任单位接单 → 整改实施 → 整改证明提交(截图/复测报告) → 平台复核 → 销号归档
- 工作流引擎需支持流程可配置(不同场景可加会签节点、分级上报节点),不建议硬编码状态机
- 支持批量派单(同一漏洞影响多个资产/单位时)
- 超期未处置自动升级机制(超过SLA自动上报至上级监管、触发通报预警)
- 整改证明支持多种验证方式:人工审核截图报告、平台发起复测扫描自动验证
- 工单需完整记录处理时间线,支撑后续统计分析(平均修复时长 MTTR)

**输入**:风险评分模块推送的风险事件、责任单位操作
**输出**:工单状态变更事件(供报表、通报模块使用)

**关键非功能要求**:
- 工作流引擎需支持流程版本管理(流程变更不影响进行中的存量工单)

---

### 3.7 通报预警模块(Notification & Alert）

**功能描述**:面向不同层级的漏洞通报、预警推送。

**详细需求点**:
- 通报分级:国家级重大漏洞通报(如0day在野利用)、行业专项通报、单位级日常告警
- 多渠道触达:平台站内信、短信网关、邮件、政务通信平台对接、第三方API推送
- 通报内容模板化(不同级别通报有固定格式规范,需支持模板管理)
- 通报送达确认机制:需记录送达状态、是否已读、责任单位响应时间
- 支持通报升级:未及时响应自动升级通报至上级或增加通报渠道

**输入**:风险评分模块的高危事件、工单超期事件、人工发起的专项通报
**输出**:通报记录、送达状态、多渠道推送请求

**关键非功能要求**:
- 极高危漏洞通报要求全国范围内5分钟内完成推送触发

---

### 3.8 统一身份认证与权限模块(IAM）

**功能描述**:全平台统一身份认证与细粒度权限控制。

**详细需求点**:
- 支持多因素认证:账号密码 + 短信/UKey/USB Key(涉密操作强制双因素)
- 角色体系:国家级管理员、行业监管员、属地监管员、企业管理员、企业填报员、审计员、公众(只读)
- 权限粒度需到**字段级/按钮级**(如同一漏洞详情页,监管角色可见完整信息,企业角色仅见与自身资产相关且脱敏的信息)
- 对接国产CA机构做身份核验(如涉及电子签名/责任认定场景)
- 单点登录(SSO)支持对接下级/兄弟单位已有的身份系统(通过标准协议如OIDC/SAML)

**关键非功能要求**:
- 涉密数据访问操作强制二次认证,不可仅靠会话保持

---

### 3.9 审计与合规模块(Audit & Compliance）

**功能描述**:全链路操作留痕,支撑安全审计与合规检查。

**详细需求点**:
- 审计范围:登录登出、数据查询、数据导出、权限变更、通报发起、工单操作、扫描任务发起
- 审计日志需包含:操作人、操作时间、操作内容、操作对象、来源IP、操作结果
- 日志防篡改:建议采用一次写入多次读取(WORM)存储或哈希链/区块链存证方式
- 支持按合规要求(等保测评、密评)导出标准格式审计报告
- 敏感数据(未公开漏洞、内部通报)的访问需要有独立的审批留痕链路,不能与普通查询日志混同

**关键非功能要求**:
- 审计日志留存时长:不少于180天在线可查,历史数据归档保存不少于3年(具体依据国家最新法规要求）

---

### 3.10 报表与数据大屏模块(Reporting & Dashboard）

**功能描述**:面向不同角色的统计分析与可视化展示。

**详细需求点**:
- 国家级大屏:全国漏洞态势热力图、行业分布、高危漏洞处置进度总览
- 行业/属地报表:辖区内漏洞数量趋势、平均修复时长、超期未处置统计、责任单位排名
- 企业自助报表:自身资产漏洞概览、整改历史、合规达标情况
- 支持报表定时生成与自动分发(周报/月报/季报)
- 支持自定义报表(拖拽式取数配置,面向数据分析人员)

**关键非功能要求**:
- 大屏数据刷新延迟不超过5分钟(准实时)

---

### 3.11 开放接口与外部对接模块(Open API & Integration）

**功能描述**:为下级系统、兄弟单位、企业自有安全平台提供标准化数据交换能力。

**详细需求点**:
- 提供标准漏洞情报订阅接口(建议参考STIX/TAXII威胁情报交换标准)
- 提供资产/漏洞数据上报API(企业可通过API批量上报资产及自查漏洞,替代纯人工填报)
- 提供Webhook机制,允许下级系统订阅特定事件(如新增高危通报)主动推送
- API需有独立的密钥管理与调用配额控制,区分内部服务调用与外部合作方调用

**关键非功能要求**:
- 开放API需有独立网关层限流策略,避免影响内部核心链路稳定性

## 4. 前端架构设计

### 4.1 多端划分

| 端 | 使用角色 | 部署方式 |
|---|---|---|
| 监管后台 | 国家级/行业/属地监管人员 | 独立子应用,内网优先 |
| 企业门户 | 企业管理员/填报员 | 独立子应用,可公网访问(经WAF) |
| 公众查询端 | 公众 | 独立轻量应用,仅展示已公开脱敏信息 |
| 数据大屏 | 各级展示场景 | 独立大屏应用,大屏专用布局 |
| 移动端 | 企业移动填报/审批 | uni-app 跨端或独立小程序 |

四个 Web 端建议采用**微前端架构**(qiankun 或 Module Federation)拆分为独立子应用,共享统一的登录态和基础组件库,但各自独立迭代部署,避免相互阻塞发版节奏。

### 4.2 前端技术栈

| 类别 | 选型 | 说明 |
|---|---|---|
| 框架 | React 18 + TypeScript 5 | 类型安全,大型团队协作首选 |
| 构建工具 | Vite 5 | 冷启动/热更新性能优 |
| 状态管理 | Redux Toolkit(复杂业务流)+ Zustand(局部轻量状态) | 按模块复杂度分层选用 |
| UI组件库 | Ant Design 5 | 政企场景组件丰富、审美贴合 |
| 数据可视化 | ECharts 5 + AntV G2/G6(关系图谱) | 用于漏洞态势图、资产关联图 |
| 表单引擎 | Formily 或自研 Schema 驱动表单 | 应对大量动态表单(漏洞上报字段随类型变化) |
| 微前端框架 | qiankun | 多子应用集成、独立部署 |
| 移动端 | uni-app | 一次开发多端(小程序+App)覆盖企业移动填报场景 |
| 国际化 | react-i18next | 面向漏洞情报的中英文双语展示 |

### 4.3 前端关键设计要求

- **权限渲染框架**:菜单、按钮、字段级权限需统一由后端下发权限树,前端基于统一 Hook/HOC 控制渲染,禁止前端硬编码角色判断逻辑
- **表单离线暂存**:漏洞上报等长表单需支持本地 IndexedDB 暂存草稿,防止意外关闭丢失数据
- **敏感数据展示脱敏**:企业端/公众端页面对未授权字段(如内部编号、原始上报人联系方式)需前端强制脱敏展示(且后端也必须同步过滤,前端脱敏仅作为体验层双保险,不能替代后端权限控制)
- **国密改造**:如需支持国密浏览器插件/证书调用(涉及电子签名场景),需预留 SM2 签名调用接口层
- **大屏适配**:数据大屏应用需支持多分辨率自适应(1920×1080 / 3840×2160 及拼接屏场景)

## 5. 后端架构设计

### 5.1 微服务清单

| 服务名 | 职责 | 建议语言 | 数据存储 |
|---|---|---|---|
| gateway-service | API网关、路由、限流熔断 | Go(高并发网关首选) | Redis(限流计数) |
| iam-service | 统一身份认证、权限管理 | Java(Spring Boot) | PostgreSQL |
| intel-collector-service | 情报采集与清洗 | Python | Kafka + MinIO(原始数据) |
| vuln-kb-service | 漏洞知识库 | Java(Spring Boot)| PostgreSQL + Elasticsearch |
| asset-service | 资产管理与测绘 | Go 或 Java | PostgreSQL + Neo4j(关联图) |
| scan-orchestrator-service | 扫描任务编排 | Go | PostgreSQL + Redis(队列) |
| risk-scoring-service | 风险评分引擎 | Python(规则引擎/模型友好) | PostgreSQL |
| workflow-service | 工单闭环工作流 | Java(集成 Flowable) | PostgreSQL |
| notification-service | 通报预警 | Go | PostgreSQL + 消息队列 |
| audit-service | 审计日志 | Java 或 Go | 独立日志库(WORM存储) |
| report-service | 报表与大屏数据 | Java 或 Python | Elasticsearch + PostgreSQL |
| open-api-service | 对外开放接口 | Go | 独立网关限流策略 |

**语言选型说明**:
- Go:适合高并发、资源敏感的网关类、编排类服务(启动快、内存占用低)
- Java(Spring Boot生态):适合业务逻辑复杂、需要成熟工作流/事务管理的服务,团队招聘和生态成熟度更高
- Python:适合情报采集(丰富的爬虫/解析生态)、风险评分(规则引擎/未来可扩展机器学习模型)

### 5.2 服务间通信设计

- **同步调用**:内部服务间用 gRPC(高性能、强类型契约),对外开放 API 用 RESTful + OpenAPI 3.0 规范文档
- **异步事件**:核心业务链路(采集→清洗→入库→评分→通报→工单)使用 Kafka 事件驱动,关键 Topic 设计如下:

```
raw.vuln.intel          原始采集情报事件
vuln.kb.updated         知识库更新事件
asset.discovered        资产发现事件
asset.vuln.matched      资产-漏洞匹配事件
risk.scored             风险评分完成事件
workflow.ticket.created 工单创建事件
workflow.ticket.overdue 工单超期事件
notification.dispatch   通报下发事件
audit.log.raw           审计日志原始事件
```

- **服务发现与配置中心**:Nacos 或 Consul,统一管理服务注册发现与动态配置
- **API 网关**:建议 APISIX 或 Kong,支持插件化限流、鉴权前置、灰度发布

### 5.3 后端关键设计要求

- 每个微服务独立数据库 schema,严禁跨服务直连对方数据库,数据共享一律通过 API 或事件
- 所有对外暴露接口必须过网关统一鉴权,内部服务间调用需基于 mTLS 双向认证
- 核心链路(情报采集→通报预警)需设计**幂等性保障**(同一 CVE 事件重复消费不应重复触发通报)
- 高危链路(风险评分批量重算、通报下发)需支持**限流与降级预案**,避免突发热点漏洞事件打垮系统

## 6. 数据库与存储设计

### 6.1 存储选型总览

| 数据类型 | 选型 | 国产化替代方案 |
|---|---|---|
| 核心业务结构化数据 | PostgreSQL 15(主从+读写分离) | openGauss / 达梦 DM8 |
| 漏洞全文检索 | Elasticsearch 8 | 如需信创认证,考虑 InfiniFlow / 需另行评估 |
| 缓存/会话/限流计数 | Redis 7 集群 | 腾讯云 TendisPlus(如走信创云) |
| 消息队列 | Kafka(或 RocketMQ) | RocketMQ 更贴合国产化生态与运维习惯 |
| 对象存储(附件/报告/原始数据) | MinIO | 兼容S3协议,私有化部署无阻碍 |
| 图数据库(资产关联/攻击面分析,可选) | Neo4j | 国产可选 NebulaGraph |
| 监控时序数据 | Prometheus + Thanos | 通用开源方案,无强合规限制 |

### 6.2 核心表结构设计(示例,PostgreSQL)

以下为关键表的简化 DDL 示例,供研发落地参考:

```sql
-- 漏洞主表(vuln-kb-service)
CREATE TABLE vulnerabilities (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    cve_id          VARCHAR(32) UNIQUE,
    cnvd_id         VARCHAR(32),
    cnnvd_id        VARCHAR(32),
    title           VARCHAR(512) NOT NULL,
    description_cn  TEXT,
    description_en  TEXT,
    cwe_type        VARCHAR(64),
    cvss_base_score NUMERIC(3,1),
    cvss_vector     VARCHAR(128),
    epss_score      NUMERIC(5,4),
    has_poc         BOOLEAN DEFAULT FALSE,
    has_exploit_wild BOOLEAN DEFAULT FALSE,
    sensitivity_level VARCHAR(16) NOT NULL DEFAULT 'internal', -- public/internal/classified
    publish_status  VARCHAR(16) NOT NULL DEFAULT 'draft',
    published_at    TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_vuln_cvss ON vulnerabilities(cvss_base_score);
CREATE INDEX idx_vuln_sensitivity ON vulnerabilities(sensitivity_level);

-- 受影响产品版本表
CREATE TABLE affected_products (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    vuln_id         UUID REFERENCES vulnerabilities(id),
    vendor          VARCHAR(128),
    product         VARCHAR(128),
    version_start   VARCHAR(32),
    version_end     VARCHAR(32),
    version_affected_exact VARCHAR(32)
);

-- 资产主表(asset-service)
CREATE TABLE assets (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    asset_identifier VARCHAR(256) NOT NULL, -- IP/域名/主机名
    asset_type      VARCHAR(32) NOT NULL,   -- server/network_device/iot/cloud
    owner_org_id    UUID NOT NULL,
    owner_person    VARCHAR(64),
    importance_level VARCHAR(16) NOT NULL DEFAULT 'medium',
    internet_exposed BOOLEAN DEFAULT FALSE,
    environment     VARCHAR(16) DEFAULT 'production',
    status          VARCHAR(16) DEFAULT 'active', -- active/offline
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_asset_org ON assets(owner_org_id);

-- 资产-漏洞关联(风险事件)表
CREATE TABLE asset_vuln_risks (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    asset_id        UUID REFERENCES assets(id),
    vuln_id         UUID REFERENCES vulnerabilities(id),
    risk_score      NUMERIC(5,2),
    risk_level      VARCHAR(16), -- critical/high/medium/low
    discovered_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    discovery_method VARCHAR(32), -- active_scan/passive/self_reported
    status          VARCHAR(16) DEFAULT 'open', -- open/in_progress/fixed/false_positive
    UNIQUE(asset_id, vuln_id)
);
CREATE INDEX idx_risk_level ON asset_vuln_risks(risk_level, status);

-- 工单表(workflow-service)
CREATE TABLE tickets (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    risk_id         UUID REFERENCES asset_vuln_risks(id),
    assigned_org_id UUID NOT NULL,
    assigned_to     VARCHAR(64),
    priority        VARCHAR(16),
    sla_deadline    TIMESTAMPTZ,
    current_stage   VARCHAR(32), -- assigned/in_progress/proof_submitted/reviewed/closed
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    closed_at       TIMESTAMPTZ
);

-- 审计日志表(audit-service,建议按月分区)
CREATE TABLE audit_logs (
    id              BIGSERIAL,
    operator_id     UUID NOT NULL,
    operator_role   VARCHAR(32),
    action_type     VARCHAR(64) NOT NULL,
    target_type     VARCHAR(64),
    target_id       VARCHAR(128),
    source_ip       INET,
    result          VARCHAR(16),
    detail          JSONB,
    occurred_at     TIMESTAMPTZ NOT NULL DEFAULT now()
) PARTITION BY RANGE (occurred_at);
```

### 6.3 数据分级分类设计要点

- `sensitivity_level` 字段贯穿漏洞、通报、审计等核心表,是权限过滤的核心依据
- 涉密级别(classified)数据禁止出现在对外 API 响应及日志明文中,需在服务层统一拦截过滤
- 建议在网关层/服务层增加统一的"数据脱敏中间件",按角色自动过滤敏感字段,避免每个服务重复实现脱敏逻辑

## 7. 基础设施与部署架构

### 7.1 部署环境

- **容器编排**:Kubernetes,信创环境建议基于 openEuler / 统信UOS 操作系统 + 国产K8s发行版(如青云KubeSphere)
- **服务网格(可选)**:Istio,适用于微服务数量多、需精细化流量治理和灰度发布的中后期阶段
- **多活容灾**:至少两地三中心部署,核心数据库(PostgreSQL)采用同步流复制,RPO 目标趋近于0,RTO 目标小于15分钟
- **网络分区**:接入层(DMZ)、应用层(内网可信区)、数据层(核心区)三层网络隔离,层间访问经防火墙/网闸严格管控

### 7.2 CI/CD

- 代码仓库:GitLab(私有化部署)
- 流水线:GitLab CI 或 Jenkins,涉密环境建议流水线本身部署在隔离网络,禁止直连互联网拉取依赖(需自建私有源镜像)
- 镜像仓库:Harbor,启用镜像签名与漏洞扫描(自我验证,平台自身也应践行左移安全)
- 发布策略:蓝绿部署或金丝雀发布,核心服务变更需灰度验证

### 7.3 监控与告警

- 指标监控:Prometheus + Grafana
- 日志聚合:ELK(Elasticsearch + Logstash + Kibana)或轻量化的 Loki + Grafana
- 链路追踪:Jaeger 或 SkyWalking,用于排查跨服务调用性能问题
- 核心告警项:服务可用性、API错误率、消息队列积压、数据库主从延迟、磁盘容量

## 8. 安全设计与合规要求

### 8.1 等级保护与密码合规

- 平台整体建设需满足**等保三级**,核心漏洞库、通报系统建议按**等保四级**要求设计
- 传输层强制使用国密 SSL(SM2密钥交换/SM3摘要/SM4对称加密)替代或并行支持国际算法
- 敏感字段(未公开漏洞详情、企业联系人信息、涉密通报内容)数据库落盘加密,建议采用国密SM4算法透明加密
- 需通过国家密码管理局认定的密评机构测评

### 8.2 身份认证与访问控制

- 统一身份认证中心对接国产CA机构,核心操作(通报发起、涉密数据导出)强制双因素认证(短信+UKey或USB Key)
- 基于 RBAC + ABAC 混合权限模型:角色决定基础权限范围(RBAC),数据属性(如数据敏感级别、所属租户)决定实际可访问数据(ABAC)
- 会话管理:强制会话超时(建议不超过30分钟无操作自动登出),涉密操作会话不可被记住/免登录

### 8.3 数据安全

- 数据分级分类贯穿全平台(见 6.3 节),按分级实施差异化访问控制与审计强度
- 数据出境/跨租户共享需有独立审批流程,不能仅靠接口权限控制
- 数据库定期备份,备份数据同样需要加密存储,备份介质管理需符合国家保密要求

### 8.4 审计与溯源

- 全链路操作审计(见 3.9 节),审计日志本身需防篡改(WORM存储或哈希链存证)
- 关键操作(未公开漏洞查看、涉密通报发起)需要"操作前二次确认+操作后即时告警管理员"机制

### 8.5 供应链与自身安全

- 平台自身所用开源组件需过 SCA(软件成分分析)扫描,建立组件漏洞库并与自身漏洞管理能力联动(自我验证示范)
- 代码上线前需过 SAST(静态代码扫描)、DAST(动态扫描)、人工代码评审三重关卡
- 定期(建议至少年度)开展平台自身的渗透测试与红蓝对抗演练

### 8.6 扫描授权边界(法律合规红线)

- 主动扫描/测绘功能必须有严格的授权范围控制机制,系统层面强制校验扫描目标是否在已授权 IP 段/域名范围内,超范围请求直接拒绝并告警
- 扫描任务发起需保留完整授权凭证记录,以应对潜在的法律追溯需求

## 10. 接口设计规范(示例)

### 10.1 API 设计通用规范

- 遵循 RESTful 风格,统一使用 `/api/v1/{resource}` 路径规范
- 统一响应结构:

```json
{
  "code": 0,
  "message": "success",
  "data": { },
  "trace_id": "req-xxxxxx"
}
```

- 所有接口需在 OpenAPI 3.0 文档中登记,网关基于文档自动生成 Mock 与校验规则

### 10.2 核心接口示例

**查询漏洞详情**
```
GET /api/v1/vulnerabilities/{cve_id}
Header: Authorization: Bearer {token}

Response 200:
{
  "code": 0,
  "data": {
    "cve_id": "CVE-2026-XXXXX",
    "title": "...",
    "cvss_base_score": 9.8,
    "risk_level": "critical",
    "affected_products": [...]
  }
}
```

**企业上报资产漏洞自查结果**
```
POST /api/v1/assets/{asset_id}/self-report
Body:
{
  "vuln_id": "CVE-2026-XXXXX",
  "status": "confirmed",
  "remediation_plan": "计划7日内完成补丁升级"
}
```

**订阅高危漏洞通报(Webhook）**
```
POST /api/v1/subscriptions
Body:
{
  "callback_url": "https://partner-system.example.gov.cn/webhook",
  "event_types": ["notification.dispatch"],
  "min_risk_level": "high"
}
```

## 11. 实施路线图建议

| 阶段 | 周期建议 | 目标 |

| 一期:基础能力建设 | 3-4个月 | 情报采集、漏洞知识库、基础IAM、审计模块上线,打通核心数据链路 |
